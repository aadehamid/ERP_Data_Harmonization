# LSC Enterprise Data Harmonization

> A synthetic, open-source-friendly benchmark and reference implementation for harmonizing enterprise data across ECC-style, S/4HANA-style, JDE-style, regional, and open-source ERP data sources.

## Overview

This project demonstrates how **Lagos Specialty Chemicals (LSC)**—a fictional multinational specialty-chemicals manufacturer and distributor—can create a governed, semantically interoperable data foundation across heterogeneous ERP and operational systems.

The project focuses on the real problem of enterprise data harmonization: the same business concepts are represented differently across systems, regions, implementations, organizational units, and local code sets. A product may be a material in one source, an item in another, a product in a third, and a customer-specific identifier in a fourth. A customer or supplier may have different identifiers, names, hierarchy levels, roles, and sites across systems. A warehouse, plant, branch/plant, legal entity, and sales organization may represent overlapping but non-equivalent organizational concepts.

The result is a reusable technical and semantic foundation that can support trusted cross-system analytics, reporting, planning, AI-assisted discovery, operational decision-making, and enterprise-wide measures. Calculating global KPIs is an important consequence of harmonized data—not the project’s sole objective.

> **Important:** Lagos Specialty Chemicals (LSC) is fictional. All data generated by this project is synthetic or derived from lawful public/open sources. Nothing in this repository is intended to represent a real company, ERP export, chemical product, safety classification, tax treatment, customer, supplier, facility, or production process.

---

## The problem

Enterprise data estates commonly include multiple ERP platforms, regional implementations, local applications, operational systems, and reporting layers. Each system may represent the same real-world concept differently.

Examples include:

| Business concept | Possible source representations |
|---|---|
| Product/material | ECC-style material, S/4-style product/material, JDE-style item, ERPNext item, OFBiz product, local SKU, customer material number |
| Customer/supplier | ECC-style customer/vendor, S/4-style Business Partner with roles, JDE-style Address Book plus customer/supplier relationships, local account or site |
| Organization | Company code, legal entity, business unit, plant, warehouse, sales organization, purchasing organization, JDE branch/plant |
| Inventory | Unrestricted stock, blocked stock, quality-held stock, allocated stock, available-to-promise, in-transit inventory, branch/plant balance |
| Commercial event | Quote, sales order, schedule line, delivery, invoice, credit, return, cancellation, backorder, allocation |
| Finance | Local account segments, reporting account, ledger, profit center, cost center, local currency, group currency, fiscal period |
| Classification | Material type, product group, JDE UDC, category code, customer segment, order type, status code, reason code |

These variations prevent straightforward integration. Simply landing data in a common lakehouse or renaming fields does not make it comparable. The project addresses the meaning, context, relationship, lineage, quality, and governance behind the data.

## Project goals

This repository will develop a reference implementation and synthetic benchmark for:

1. **Canonical enterprise modeling** — Represent common business entities, relationships, events, and measures at an enterprise level.
2. **Multi-ERP source modeling** — Generate and ingest ECC-style, S/4HANA-style, JDE-style, and open-source ERP source representations.
3. **Master-data harmonization** — Resolve products/materials, customers, suppliers, organizations, locations, alternate identifiers, roles, and hierarchies.
4. **Reference-data harmonization** — Govern units of measure, packaging units, currencies, countries, statuses, classifications, tax concepts, and local code sets.
5. **Semantic interoperability** — Use a business dictionary, ontology, SKOS taxonomies, crosswalks, mappings, data contracts, and provenance.
6. **Regional context** — Model valid differences in country, legal entity, fiscal calendar, currency, language, tax context, organization, and local configuration.
7. **Data quality and lineage** — Detect defects, manage exceptions, reconcile results, and trace conformed data to source records and approved mapping rules.
8. **AI-assisted harmonization** — Evaluate deterministic rules, traditional ML, and retrieval-augmented LLMs for mapping discovery, entity resolution, code interpretation, and explanation.
9. **Reusable data products** — Produce conformed data products that can support finance, commercial, supply-chain, inventory, manufacturing, reliability, customer-service, and later KPI/measure use cases.

## LSC benchmark context

LSC is a **fictional specialty-chemicals manufacturer and distributor** used as a realistic business scenario for the synthetic dataset.

### Initial business model

LSC:

- Procures raw materials, intermediates, packaging, and indirect materials from suppliers.
- Manufactures, blends, packages, and distributes specialty materials.
- Operates multiple legal entities, manufacturing sites, warehouses, sales organizations, purchasing organizations, and branch/plant structures.
- Sells materials to industrial customers across regions.
- Maintains product/material, customer/supplier, inventory, commercial, procurement, finance, and quality-related records in multiple source-system representations.
- Uses customer-specific material identifiers, product grades, package configurations, alternate/substitute materials, and local classifications.

The scenario provides enough complexity to test master-data, reference-data, process, finance, and regional harmonization. Any chemical, quality, packaging, safety, regulatory, tax, or operational values are synthetic illustrative data—not production or compliance content.

## Architecture

```text
Public/open seeds + fictional LSC reference data + open-source ERP lab data
                              |
                              v
                 LSC canonical enterprise truth
      - Stable enterprise identities and relationships
      - Product/material, party, organization, location, and event model
      - Reference data, taxonomy, regional policy, and known truth
                              |
          +-------------------+-------------------+
          |                   |                   |
          v                   v                   v
   ECC-style profiles   S/4-style profiles   JDE-style profiles
          |                   |                   |
          +-------------------+-------------------+
                              |
                              v
            Source semantic adapters and mapping services
                              |
                              v
       Conformed/mastered data products and semantic layer
                              |
                              v
  Quality, reconciliation, lineage, comparability, analytics, and AI agents
```

The canonical truth layer is essential. It ensures all source-system representations derive from the same underlying fictional business reality, enabling objective evaluation of mapping correctness, entity resolution, transformation quality, and reconciliation.

## Core principles

- **Harmonize meaning, not just schema.** A common column name does not guarantee a common business meaning.
- **Preserve source and regional context.** System, instance, organization, legal entity, country, code scheme, and effective date can change interpretation.
- **Use known ground truth.** Synthetic generation supports measurable evaluation of mappings, matches, data quality, and AI proposals.
- **Keep the pilot small first.** Semantic correctness, governance, lineage, quality, and reconciliation come before large data volumes.
- **Retain source evidence.** Derived/conformed records must retain source IDs, source context, mapping version, transformation run, and quality status.
- **Separate semantic assets by role.** The glossary defines terms; ontology models durable concepts/relationships; taxonomies classify; mappings operationalize source-to-target semantics.
- **Rules execute; AI assists.** Deterministic approved mappings produce certified output. ML/LLMs propose, rank, match, retrieve evidence, and explain under stewardship controls.
- **Do not force false comparability.** Record where data is comparable, adjusted, partially comparable, non-comparable, or pending validation.
- **Use synthetic and lawful data.** Do not commit real customer, employee, supplier, pricing, formula, operational, financial, or production data.

## Initial scope

The first benchmark release will focus on a linked business slice:

```text
Product/material
  + party/customer/supplier
  + legal entity/organization/location
  + sales order and fulfillment
  + purchase order and receipt
  + inventory position and movement
  + invoice and financial posting
  + UoM, packaging, currency, time, status, and reference data
```

### Initial source profiles

| Profile | Purpose |
|---|---|
| `ecc_style_us01` | Synthetic ECC-inspired U.S. representation with separate customer, vendor, material, organization, and inventory perspectives |
| `s4_style_global01` | Synthetic S/4-inspired global representation with Business Partner identity and customer/supplier roles |
| `jde_style_us01` | Synthetic JDE-inspired U.S. representation with Address Book, item, branch/plant, UDC, and category-code patterns |
| `erpnext_lab01` | Actual fictional data generated in a local ERPNext environment |
| `ofbiz_lab01` | Actual fictional data loaded through controlled Apache OFBiz fixtures |

### Initial scale

The project starts with manageable volume, such as:

- 100–2,000 materials/products.
- 100–5,000 parties.
- 10–100 organizations and locations.
- 1,000–100,000 sales-order lines.
- Related purchase, inventory, delivery, invoice, and journal events.

Large TPC-H scale factors and billion-row workloads are optional future engineering work, not prerequisites.

## Synthetic data strategy

The complete design is in [Synthetic Data Generation Strategy](docs/synthetic-data-generation-strategy.md). In summary:

1. Create fictional LSC enterprise truth: stable IDs, master data, organizations, events, policies, and relationships.
2. Generate source-system variants from that truth, rather than independently.
3. Add regional variations, code schemes, hierarchy differences, role patterns, UoM/packaging/currency/time differences, and local process states.
4. Inject controlled data defects and semantic ambiguity.
5. Preserve source-to-canonical mappings, entity-match truth, quality labels, transformation lineage, and expected reconciliation results.
6. Separate development/training artifacts from held-out evaluation truth.

## Semantic assets

The project will use:

- **Business dictionary/glossary** for terms, definitions, owners, policy, examples, and source interpretation.
- **Canonical data models** for implementation-ready entities, attributes, keys, and grain.
- **Ontology** for stable business concepts and durable relationships.
- **SKOS taxonomies** for product/material classifications, source code schemes, organization, finance, statuses, UoM, currencies, and reference data.
- **Mapping specifications** for source-to-canonical rules, transformations, effective dates, source context, approvals, and lineage.
- **SHACL/data contracts** for semantic and structural validation.
- **PROV-O-aligned lineage** for source, mapping, transformation, and output provenance.

Useful reference standards:

- [SKOS](https://www.w3.org/TR/skos-reference/)
- [SHACL](https://www.w3.org/TR/shacl/)
- [PROV-O](https://www.w3.org/TR/prov-o/)

## AI and ML approach

The project will evaluate a hybrid semantic-mapping architecture:

```text
Glossary + ontology + taxonomy + approved mappings
                    |
                    +--> Deterministic transformation execution
                    +--> ML ranking and entity-resolution scoring
                    +--> Retrieval-augmented LLM mapping proposals and explanations
                    |
                    v
      Human stewardship, validation, approval, versioning, and testing
                    |
                    v
          Certified conformed data products and analytical consumption
```

### Deterministic rules

Approved mappings, crosswalks, UoM conversions, status translations, finance transformations, and quality rules execute certified transformations.

### Traditional ML

ML can rank candidate field mappings, score entity matches, detect anomalies, and rank reference-data crosswalk candidates.

### LLMs

LLMs can interpret sparse metadata, local code descriptions, custom fields, documentation, and candidate semantic transformations. They must return structured, evidence-grounded proposals and cannot autonomously publish mappings or redefine enterprise concepts.

## Getting started

### 1. Read the strategy

Start with [Synthetic Data Generation Strategy](docs/synthetic-data-generation-strategy.md).

### 2. Create the planned structure

Create the directories shown above, especially `docs/`, `scenarios/`, `generators/`, `schemas/`, `ontology/`, `taxonomies/`, `mappings/`, `sample-data/`, and `tests/`.

### 3. Build the thin slice

Generate a small fictional LSC dataset:

- 100 materials.
- 100 parties.
- 10 locations.
- 1,000 sales-order lines.
- ECC-style, S/4-style, and JDE-style source files.

### 4. Validate the lifecycle

For a representative product, customer, order line, and inventory movement, prove:

```text
Source record
  -> source profile/context
  -> mapping rule
  -> canonical entity/event
  -> conformed record
  -> data-quality outcome
  -> reconciliation result
  -> transformation/generator provenance
```

### 5. Expand incrementally

Add regional context, reference data, defects, ERPNext/OFBiz lab sources, mapping evaluation, ML/LLM assistance, and only later performance scale.

## Data and usage policy

- Do not commit real production data, personally identifiable information, confidential business information, credentials, secrets, ERP database volumes, or internal mappings.
- Use only synthetic data, openly licensed data, or data approved for the repository’s intended use.
- Record source licenses, terms, attribution, and checksums for all acquired inputs.
- Keep hidden evaluation truth out of public development paths.
- Clearly mark ERP-inspired synthetic profiles as synthetic and not vendor database replicas.
- Treat all chemical, safety, regulatory, tax, accounting, quality, and operational information as fictional benchmark content—not advice or production guidance.

## Roadmap

### Phase 1 — Semantic thin slice

- Establish canonical LSC truth model.
- Generate ECC-style, S/4-style, and JDE-style sample sources.
- Define initial glossary, taxonomy, ontology, mappings, quality rules, lineage, and reconciliation tests.

### Phase 2 — Pilot benchmark

- Add regional variation, material/customer/supplier master-data complexity, reference-data crosswalks, finance, inventory, and procurement.
- Deploy ERPNext and/or OFBiz with fictional LSC fixtures.
- Build development and hidden evaluation packages.

### Phase 3 — AI-assisted harmonization

- Add mapping candidate ranking, entity-resolution scoring, retrieval-augmented LLM proposals, validation gates, and evaluation harnesses.

### Phase 4 — Optional scale and operations

- Increase transaction volumes only for defined engineering objectives.
- Add manufacturing, maintenance, quality, incident, production, and reliability domains.
